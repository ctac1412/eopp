## 3. Варианты тестирования

### Вариант A: Встроенный mock в контент-скрипт (переопределение fetch)

**Суть:** Пatches `window.fetch` в content script или через injected script. При совпадении URL возвращает заранее заготовленный JSON.

**Реализация:**
```typescript
// В content script перед запуском pipeline:
const originalFetch = window.fetch;
const mocks: Record<string, { status: number; body: unknown }> = {
  'GET*/AvailableSlots': { status: 200, body: slotsFixture },
  'POST*/captcha': { status: 200, body: captchaFixture },
  'POST*/captcha-validate': { status: 200, body: { successToken: 'test123' } },
  'POST*/Reschedule': { status: 200, body: rescheduleSuccessFixture },
};

window.fetch = async (url, init) => {
  const key = `${init?.method || 'GET'}*${url.toString()}`;
  const mock = Object.entries(mocks).find(([k]) => key.match(new RegExp(k)));
  if (mock) {
    return new Response(JSON.stringify(mock[1].body), { status: mock[1].status });
  }
  return originalFetch(url, init);
};
```

| Параметр | Оценка |
|----------|--------|
| Трудность реализации | **2/10** — простой patch fetch |
| Трудность поддержки | **3/10** — fixture'ы в одном файле, легко обновлять |
| Изоляция | Средняя — нужно восстанавливать fetch после теста |
| Coverage | Только happy path + ручные ошибки |
| Credentials/cookies | ❌ Не работают — mock возвращает Response без cookie handling |

### Вариант B: Mock Service Worker (MSW)

**Суть:** MSW перехватывает запросы на уровне Service Worker. Работает в browser context.

**Проблема:** MSW работает в main world, а content script — в isolated world. Content script использует `fetch` из isolated world, который НЕ перехватывается MSW. Для работы нужно инжектировать MSW setup script в main world через `<script>` тег.

| Параметр | Оценка |
|----------|--------|
| Трудность реализации | **6/10** — нужно инжектировать MSW в main world + синхронизировать |
| Трудность поддержки | **4/10** — MSW имеет хорошую DX, но интеграция с extension сложная |
| Совместимость с MV3 | ⚠️ Service Worker extensions могут конфликтовать |
| Coverage | Высокий — можно mock'ать любые URL |

### Вариант C: Локальный mock-сервер

**Суть:** Запустить локальный HTTP-сервер (Node.js/Python), который отдаёт fixture'ы на те же пути, что и EOPP API. Перенаправить запросы через:
- `hosts` файл (перенаправить `eopp.epd-portal.ru` на `127.0.0.1`)
- Или proxy extension
- Или изменить base URL в `constants.ts`

**Реализация (Node.js, ~100 строк):**
```typescript
import express from 'express';
const app = express();
app.use(express.json());

app.get('/reservations-api/v1/timeslot/AvailableSlots', (req, res) => {
  res.json(slotsFixture);
});
app.post('/reservations-api/v1/captcha', (req, res) => {
  res.json(captchaFixture);
});
// ... остальные эндпоинты
app.listen(9999);
```

| Параметр | Оценка |
|----------|--------|
| Трудность реализации | **3/10** — простой Express/FastAPI сервер |
| Трудность поддержки | **2/10** — fixture'ы как JSON файлы, сервер — trivial |
| Credentials/cookies | ✅ Работают (сервер может ставить cookies) |
| Гибкость | Высокая — можно возвращать разные ответы в зависимости от body |
| Запуск | Нужно держать сервер + менять hosts или base URL |

### Вариант D: Chrome DevTools Protocol (CDP)

**Суть:** Через CDP (`Chrome.debugger` API или `cdp` npm пакет) перехватывать и подменять network requests на лету.

**Реализация:**
```typescript
// Через extension debug API или внешний скрипт
const CDP = require('chrome-remote-interface');
CDP(async (client) => {
  const { Network, Fetch } = client;
  await Fetch.enable();
  Fetch.requestPaused(({ requestId, request }) => {
    if (request.url.includes('/reservations-api/')) {
      const body = JSON.stringify(fixtureFor(request.url));
      await Fetch.fulfillRequest({ requestId, responseCode: 200, body: btoa(body) });
    } else {
      await Fetch.continueRequest({ requestId });
    }
  });
});
```

| Параметр | Оценка |
|----------|--------|
| Трудность реализации | **7/10** — CDP API сложный, нужно remote-debugging порты |
| Трудность поддержки | **8/10** — хрупкий, зависит от версии Chrome |
| Автоматизация | ✅ Отлично для E2E тестов |
| Daily dev | ❌ Неудобно — нужно запускать Chrome с `--remote-debugging-port` |

**Реализация:**
```typescript

test('pipeline runs with mocks', async ({ context }) => {
  await context.addInitScript(() => {
    // Моки или установка test mode

  const page = await context.newPage();
  await page.route('**/reservations-api/v1/timeslot/AvailableSlots', route => {
    route.fulfill({ json: slotsFixture, status: 200 });
  });
  await page.route('**/reservations-api/v1/captcha', route => {
    route.fulfill({ json: captchaFixture, status: 200 });

  await page.click('[data-testid="run-injector"]');
  // Проверить результат

```

### Вариант F: Unit-тесты отдельных функций (Vitest)

**Суть:** Тестировать функции `stages.ts` и `pipeline.ts` изолированно, заменив `httpRequest` на mock.

**Реализация:**
```typescript
import { describe, it, expect, vi } from 'vitest';
import { getAvailableSlots } from './stages';

vi.mock('./client', () => ({
  httpRequest: vi.fn(),
  retryOn429: vi.fn((fn) => fn()),
}));

describe('getAvailableSlots', () => {
  it('returns slots', async () => {
    mockHttpRequest.mockResolvedValue(slotsFixture);
    const result = await getAvailableSlots(config);
    expect(result.slots).toHaveLength(3);
    expect(mockHttpRequest).toHaveBeenCalledWith('GET', expect.stringContaining('AvailableSlots'));
  });
});
```

|----------|--------|
| Трудность реализации | **2/10** — Vitest + vi.mock() — тривиально |
| Трудность поддержки | **1/10** — стандартный подход, легко поддерживать |
| Speed | ~50ms на тест |
| CI | ✅ Идеально |

## 5. Рекомендация

### Комбинация: **F (Unit-тесты) + C (Mock-сервер)**

### Почему именно такая комбинация:

#### 1. Unit-тесты (Vitest) — основа
- **Быстро** (~50ms), **надёжно**, **CI-friendly**
- Тестируют логику `selectBestSlot()`, `runFromStage2()` (контроль runUpTo), обработку `AllSlotsOccupiedOnInterval`
- Мок `httpRequest` через `vi.mock()` — 5 минут настройки
- Покрывают 80% кодовой базы pipeline

#### 2. Mock-сервер (Express) — интеграционные тесты
- **Полный цикл**: content script → background.js → mock-сервер
- Тестирует port-based messaging (критично для MV3)
- Тестирует retryOn429, slot retry logic
- Fixture'ы легко обновлять — просто JSON файлы
- Можно запускать вручную для отладки: `npm run test-server`

#### Почему не Playwright (E):
- Playwright для browser extensions — боль: нужно упаковывать extension, устанавливать, работать с popup/content scripts
- Для текущей задачи (тестирование pipeline логики) это overkill
- Можно рассмотреть в будущем для регрессионного E2E тестирования

#### Почему не MSW (B):
- Content script isolated world не видит Service Worker intercepts
- Требуется инжекция в main world — сложно и хрупко

#### Почему не CDP (D):
- Слишком сложно для daily use
- Требует special Chrome flags
- Не подходит для CI
