# Анализ: Ручное решение капчи в модалке плагина

## Цель

Перенести UI для **ручного решения капч** из React-фронтенда (страница `/`) в модалку browser extension. Алгоритм автоматического решения (`captcha_solver.py`) остаётся на Python-сервере. Бэкенд не меняется.

## 2. Как доставлять капчи в модалку

### Проблема

React-фронтенд подписывается на SSE `new EventSource('/stream')` напрямую, потому что работает на том же origin (`china.alabai.netcraze.pro`). Content script выполняется на `eopp.epd-portal.ru` и **не может** открыть SSE-соединение на другой домен из-за CORS ограничений EventSource (не поддерживает кастомные заголовки, credentials behave differently).

### Варианты

#### Вариант A: Background worker как SSE-мост (РЕКОМЕНДУЕТСЯ)

Background service worker открывает `fetch`-соединение с `/stream`, парсит SSE-поток, ретранслирует события в content script через port.

**Архитектура:**
```
Python сервер  --SSE /stream-->  background.js  --port.postMessage-->  content script (модалка)
```

**Реализация в background.js:**
- При подключении порта с action `subscribeSSE`, background открывает persistent fetch к `/stream`
- Парсит SSE manually (читает chunks, ищет `data: ...`, `\n\n`)
- Проксирует все события через `port.postMessage({ type: 'sse', data: parsedJson })`
- При отключении порта — закрывает SSE

**Плюсы:**
- Реал-тайм доставка, 0 задержки
- Соответствует существующей архитектуре (port-based messaging уже используется)
- Background worker живёт независимо от content script lifecycle
- Один SSE-поток на активную вкладку

**Минусы:**
- Нужно реализовать SSE parser в background.js (fetch + ReadableStream, ~40 строк)
- Service worker может быть suspend-нут при долгой неактивности (MV3), но SSE fetch держит его живым

**Оценка:** 1-2 часа

---

#### Вариант B: Polling через background

Content script периодически опрашивает сервер через background на новые нерешённые капчи.

**Плюсы:**
- Проще реализовать (ordinary fetch, нет streaming)

**Минусы:**
- Задержка 1-2с до появления капчи в UI (критично при таймауте 10с)
- Лишние запросы к серверу
- Нужно новый эндпоинт `GET /pending-captchas` или хак с существующими

**Оценка:** не рекомендуется

---

#### Вариант C: Новый эндпоинт callback/webhook

Сервер при создании капчи делает обратный вызов на плагин. Неприменимо — плагин не имеет публичного URL.

---

### Решение: Вариант A

Добавить в `background.js` обработку action `subscribeSSE`:

```js
// background.js — новый блок
else if (msg.action === 'subscribeSaptcha') {
  // Открываем SSE к серверу
  const SSE_ACTION = 'subscribeSse';
  // ... fetch + ReadableStream parser → port.postMessage
}
```

В `src/api/background.ts` добавить:
```ts
export function subscribeSse(onMessage: (data: unknown) => void): () => void {
  const port = chrome.runtime.connect({ name: `sse-${Date.now()}` });
  port.postMessage({ action: 'subscribeSse', serverUrl: getServerUrl() });
  port.onMessage.addListener((resp) => {
    if (resp.type === 'sse') onMessage(resp.data);
  });
  return () => port.disconnect();
}
```

## 3. Как отправить выбор обратно

### Существующий механизм

React-фронтенд при клике на карточку делает:
```js
fetch('/solve', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ captcha_id: entry.id, variantIndex: parseInt(index) }),
})
```

Эндпоинт `POST /solve` (`src/routes.py:229`):
1. Находит капчу в `pending[captcha_id]`
2. Извлекает `tile_ids` из `entry["variants"][variant_index]`
3. Записывает `entry["result"]`, вызывает `entry["event"].set()` — это **разблокирует** заблокированный `/solve-captcha`
4. Пушит SSE `captcha_solved`
5. Возвращает `{ variantIndex, variantTiles, resultFile }`

### Для плагина

Использовать тот же эндпоинт, но через background-прокси (cross-origin). Добавить action `solve` в `background.js`:

```js
// background.js
else if (msg.action === 'solve') {
  res = await fetch(`${serverUrl}/solve`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(msg.payload),  // { captcha_id, variantIndex }
  });
}
```

В `src/api/background.ts`:
```ts
export async function solveCaptchaManual(captchaId: string, variantIndex: number): Promise<unknown> {
  return sendMessageToBackground('solve', { captcha_id: captchaId, variantIndex });
}
```

**Ничего нового на сервере не нужно.** Эндпоинт `/solve` уже существует и работает.

## 5. Синхронизация с pipeline

### Текущий поток при autoSolve=false

```
pipeline.ts: main()
  → getAvailableSlots()                    // этап 1
  → runFromStage2(slotsResponse)
    → selectBestSlot()
    → generateCaptcha()                    // этап 2: POST /captcha на EOPP
    → solveCaptcha(captchaData, false, ...) // этап 3: POST /solve-captcha на наш сервер
       │
       │  ← СЕРВЕР БЛОКИРУЕТСЯ здесь на 10 секунд
       │     Одновременно сервер пушит SSE new_captcha
       │
       ▼
    ← Ждём ответ (variantIndex, variantTiles)
    → validateCaptcha()                    // этап 4
    → submitReschedule/Create()            // этап 5
```

**Критический момент:** `solveCaptcha()` в `stages.ts:44` — это async функция, которая делает `sendMessageToBackground('solveCaptcha', payload)`. Background делает fetch к `/solve-captcha`. Сервер блокирует это соединение. Promise не resolve-ится пока кто-то не вызовет `POST /solve` или не истечёт таймаут.

### Что нужно сделать

1. **До вызова `solveCaptcha()`** (когда `autoSolve === false`) — подписаться на SSE через background.
2. **Когда пришло SSE `new_captcha`** — сохранить данные в store, показать CaptchaGrid в модалке.
3. **Пользователь кликает вариант** → `POST /solve` через background → сервер разблокирует `/solve-captcha` → `solveCaptcha()` resolve-ится → pipeline продолжается.
4. **Если пришло SSE `captcha_timeout`** → скрыть грид, `solveCaptcha()` вернёт null → pipeline выбросит ошибку.

### Конкретная интеграция

#### В store.ts — добавить captcha-состояние

```ts
interface CaptchaState {
  activeCaptcha: {
    id: string;
    images: Record<string, string>;
    top3: string[];
    createdAt: number;
    timeout: number;
  } | null;
  setCaptcha: (captcha: CaptchaState['activeCaptcha']) => void;
  clearCaptcha: () => void;
}
```

#### В stages.ts solveCaptcha() — запуск SSE перед блокировкой

```ts
export async function solveCaptcha(captchaData, autoSolve, apiKey, reservationId) {
  log('Этап 3: запрос к нашему серверу /solve-captcha');
  useInjectorStore.getState().setStage('solving');

  // Если ручной режим — подписываемся на SSE для получения капчи
  if (!autoSolve) {
    startCaptchaSse();  // подписка → сохранение в store → рендер грида
  }

  try {
    const response = await sendMessageToBackground('solveCaptcha', payload);
    // ... обработка ответа
  } finally {
    if (!autoSolve) {
      stopCaptchaSse();  // отписка
    }
  }
}
```

#### Альтернатива: SSE на уровне модалки (не привязано к pipeline)

Подписка на SSE живёт постоянно, когда модалка открыта. При получении `new_captcha`:
- Если pipeline в стадии `solving` — показываем грид поверх текущего состояния
- Клик по варианту → `POST /solve` → pipeline продолжается

Этот подход более декупированный, но требует координации: грид должен показываться только когда pipeline ждёт решения.

**Рекомендация:** SSE на уровне модалки, постоянно активная. Проще, надёжнее, и позволяет показывать капчи даже вне pipeline (например, для тренировки).

## 8. Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Service worker suspend-ится, SSE-поток рвётся | Средняя | Реконнект в background.js при разрыве; MV3 держит worker живым при активном fetch stream |
| Race condition: капча пришла, но модалка не открыта | Низкая | SSE-данные сохраняются в store; если модалка откроется позже — капча отобразится |
| Несколько вкладок с модалкой получают одну капчу | Низкая | `/solve` idempotent — первый ответ wins, остальные получают 404 |
| Таймаут 10с слишком мал для пользователя | Средняя | Это ограничение сервера (`CAPTCHA_TIMEOUT`), не связано с UI |
