Устойчивость (Race Conditions, Deadlocks, State Loss)

#ПроблемаСерьёзностьРекомендация
7 Race condition в pending dict — два запроса с одинаковым hash перезаписывают event, первый клиент висит вечно (captcha.py:382) Критично pending.setdefault() + проверка: если entry уже существует — вернуть существующий event
8 Thread-pool истощается — threading.Event.wait() в asyncio через run_in_executor() (max 100). При 100+ параллельных капчах — deadlock Критично Заменить на asyncio.Event + asyncio.wait_for(). Убрать run_in_executor
9 push_sse держит глобальный threading.Lock на всё время итерации по всем очередям Высоко Шардировать очереди по api_key_id % N или перейти на asyncio.Queue + asyncio.gather
10 In-memory state теряется при рестарте: pending, distribution_states, sse_queues, chat_history, scheduled_events, _slot_order Высоко Критические состояния → Redis (TTL ключи). SSE очереди не сохранять
11 No TTL cleanup для distribution_states — утечка памяти если timeout handler не отработал Высоко Фоновая задача _cleanup_stale_distributions() каждые 30с
12 Смешивание threading.Lock и asyncio.Lock (operator.py:20,40) — потенциальный deadlock Средне Унифицировать: весь async-код использует только asyncio.Lock
13 init_db() глотает все ошибки миграций (db/init.py:30) — сервер стартует с битой схемой Критично raise RuntimeError("Migration failed") from e — fast-fail
14 Два глобальных DB_PATH (connection.py и entities/base.py) — могут разойтись → запись в разные файлы Критично Единый источник: constants.py → DB_PATH, обе точки ссылаются на него
15 Usage-count race: validate_key проверяет usage_count >= max_uses без блокировки → два usage пройдут лимит Высоко UPDATE ... WHERE id = ? AND usage_count < max_uses RETURNING * в одной транзакции
16 Нет circuit breaker для EOPP API (403 access challenge) и rucaptcha Средне Счётчик ошибок с экспоненциальным backoff и автовосстановлением через 30с
17 Расширение: нет fetch timeout в background.js — service worker висит до 30с Высоко AbortSignal.timeout(15000) для всех fetch в background

Роли и доступы

#ПроблемаСерьёзностьРекомендация
24 Плоская модель прав: один булев флаг is_admin + хардкод-токен 13243546. Нельзя разграничить: кто управляет тарифами, кто — ключами, кто — payout'ами Высоко Ролевая модель на api_keys.admin_role:

Иерархия:
super_admin → manager

super_admin (высший):
• назначать/снимать admin_role у любого ключа
• видеть и удалять других super_admin
• всё что может manager

manager:
• CRUD ключей (кроме смены admin_role)
• биллинг: тарифы, счета, payout'ы, prepaid
• пользователи, операторы, капчи, бенчмарки
• НЕ может повышать до super_admin

Детали реализации:
• миграция: ALTER TABLE api_keys ADD COLUMN admin_role TEXT
• существующие is_admin=1 → admin_role='manager'
• check_admin_token → get_admin_role(token)
• middleware: запрет PATCH admin_role для manager
• фронтенд: скрыть/disable кнопку смены роли для manager
• /admin/auth возвращает {ok: true, role: "super_admin"|"manager"}
25 Admin auth bypass во фронтенде — любой HTTP 200 считается валидным логином Высоко Проверять res.json().valid === true; не сохранять токен при неудаче

27 Расширение: API ключ в localStorage открытым текстом Средне chrome.storage.local + session-only или минимально btoa()
28 Фронтенд: admin token в localStorage — XSS утечка Средне httpOnly cookie с Secure; SameSite=Strict
