# EOPP Implementation Plan

Дата старта: 2026-05-22

## Принципы

- Не деплоить и не публиковать расширение без отдельной команды.
- Делать изменения небольшими блоками и коммитить завершенные задачи отдельно.
- Если вопрос не блокирует реализацию, фиксировать его в TODO и продолжать.
- Не смешивать чужие незавершенные правки с новыми изменениями без необходимости.

## Фаза 1. Shared Slots

Цель: при параллельном запуске нескольких клиентов только первый клиент с одинаковым запросом `AvailableSlots` обращается к EOPP, а остальные получают опубликованный ответ через наш backend и продолжают pipeline.

1. Backend:
   - in-memory группы с TTL;
   - `claim`, `wait`, `publish`, `fail`;
   - защита от публикации не-мастером;
   - fallback на прямой запрос у клиента при таймауте/ошибке.

2. Extension:
   - feature toggle в настройках;
   - стабильный client id в `localStorage`;
   - fingerprint группы по фактическому URL `AvailableSlots`;
   - старое поведение полностью сохраняется при выключенном toggle.

3. Проверка:
   - backend tests для master/slave сценария;
   - TypeScript typecheck расширения.

## Фаза 2. Финансовая админка

Цель: привести вкладки финансов к единому уровню с журналом: фильтры, быстрые сводки, понятные строки, меньше ручного анализа.

1. Счета:
   - проверить текущие данные и API;
   - добавить фильтры по статусу, компании, периоду, поиску;
   - добавить сводные карточки: количество, сумма, оплачено, ожидает оплаты/просрочено;
   - улучшить таблицу без изменения backend-контрактов, если данных хватает.

2. Расходы:
   - добавить фильтры по категории, периоду, поиску;
   - добавить аналитику по сумме, количеству, среднему чеку, разбивке по категориям;
   - улучшить пустые/загрузочные состояния.

3. Выплаты:
   - изучить модель выплат и доступные поля;
   - переработать визуал строк;
   - добавить фильтры, аналитику и посрочное представление;
   - оставить CRUD совместимым с текущими API.

## Фаза 3. Капчи и бенчмарки

Цель: восстановить доверие к benchmark-набору и подготовить нормальную разметку.

1. Проверить `data/captcha_examples/valid` и `data/captcha_examples/no_valid`:
   - валидность JSON;
   - наличие `valid_index`;
   - диапазон `valid_index` относительно вариантов;
   - случаи, где `valid_index: 0` мог означать "не размечено".

2. Найти место, где пример попадает в valid без сохраненного варианта, и починить.

3. Разложить примеры по папкам:
   - размеченные корректные в `valid`;
   - неразмеченные/битые в `no_valid`.

4. Запланировать frontend labeling mode:
   - отдельный режим запуска или вкладка админки;
   - более длинный таймаут;
   - сохранение выбранного варианта в JSON/БД;
   - обучение на смеси сложных и простых примеров.

## Фаза 4. Расширение UI

Цель: снизить нагрузку на EOPP и сделать UI расширения понятнее.

1. Осмотреть frontend расширения:
   - предложить и, где безопасно, реализовать компактный UI;
   - скрыть редко меняемые настройки по умолчанию;
   - улучшить статусы pipeline.

## Фаза 5. Биллинг

Цель: корректно считать новые сценарии клиентов.

1. Тарифы по времени:
   - добавить возможность отличать бронь в 10:00 от брони в 12:00;
   - предусмотреть тариф "бронь в 12" или правило по временному окну;
   - не ломать существующую тарификацию по типу действия.

2. Открытый счет:
   - для компании всегда есть один открытый счет;
   - новые usage-записи попадают в открытый счет;
   - при выписке счета он закрывается/фиксируется, затем создается новый открытый.

3. Предоплаченный пакет:
   - сущность предоплаты с балансом денег и/или количеством действий;
   - списание по тарифу при подтверждении логов;
   - связь списаний с usage-записями;
   - понятное отображение остатка.

## Фаза 6. Telegram и отчеты

Цель: уведомления и короткая ежедневная сводка без захода в админку.

1. Telegram bot:
   - изучить минимальную интеграцию без деплоя;
   - команды: статус, последние логи, итоги дня, включение/отключение уведомлений;
   - события: запуск лога, успешное завершение, ошибка.

2. Scheduled report:
   - отчет в 12:03 по Москве;
   - количество успешных действий за день;
   - сумма по тарифам;
   - разбивка по компаниям/типам действий.

## Проверка

- Frontend: `npm run build` в `frontend/`.
- Extension: `npm run typecheck` и, при необходимости, `npm run build` в `extension/`.
- Backend/tests: `uv run pytest` для затронутых backend-блоков.
- Для benchmark-аудита: отдельный отчет со списком перемещенных/исправленных captcha examples.
